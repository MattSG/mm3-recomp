# Evaluation: TGP482/XboxXBERecomp vs our xboxrecomp fork

Read on 2026-10-30 from a shallow clone (HEAD `91146ff`, 69 commits from 2026-10-10 to 2026-10-27, MIT).
Nothing from it was built or run; every claim below is from reading its README, headers and sources,
or from our own measurements (marked *ours*).

## What it is

A newer, independent Xbox static recompiler plus runtime: x86 to C++ (Zydis), built with Clang/LLD, the Xbox
kernel and XDK libraries implemented at **API level** on Windows, native **Direct3D 12** renderer, XAudio2 audio,
SDL3 only for window/input. Three games ported so far (Splinter Cell: Double Agent, BLACK, 007: From Russia With
Love). It does not use xemu code.

## How it differs from our stack

| | XboxXBERecomp | our fork (sp00nznet/xboxrecomp lineage + MM3 mods) |
|---|---|---|
| GPU | D3D8 calls (68 `D3DDevice_*`, found in the game by signature) fed to a `gpu::Backend` (Clear/Draw/Copy/Present with a `State` struct); D3D12 only | the game's own statically linked D3D library runs recompiled against an emulated NV2A; pushbuffer executor decodes methods; D3D11 ubershader, plus an SDL3_GPU backend |
| Platforms | Windows (D3D12, XAudio2); a headless Linux harness with no GPU | Windows D3D11, Windows and Linux SDL3_GPU |
| Audio | DirectSound HLE mixed in software to XAudio2 | APU/DSP emulation (GP/EP interpreter) |
| XDK builds | 4831 and 5849 only | whatever the game has: MM3 is **5233** with `D3D8LTCG` |
| CPU ABI | every function takes `X86Context&` and a base pointer, flags in locals, x87 as `double st[8]` + `top` in the context | translated C with register locals spilled around calls, x87 stack in thread-local state |
| Game code | built into `<exe>.dll` on the player's PC from their XBE | generated by `scripts/setup.py` on the player's PC |

## Should we switch? No.

1. **MM3 is not supported.** Its signature files cover only builds 4831/5849 (about 100 D3D signatures each).
   Their README says a new build needs `layout.toml` and signatures "from titles whose configs are complete",
   so MM3 would have to be ported by hand first (config, symbols, hooks) before signatures for 5233 exist.
2. **The graphics layer is not our bottleneck.** *Ours* (mm3-perf notes): race ~164 fps uncapped, game thread
   bound at about 6 ms by translated guest code, the pushbuffer executor about 4 ms on its own thread with headroom.
   Replacing the NV2A path with API-level HLE would remove at most that executor cost, not the 6 ms.
3. **Every graphics mod works on NV2A-level state.** Widescreen HUD placement, sky, distance fog, flare depth and
   draw distance read `NvD3DState`, vertex-program constants and combiner configs. They would all need re-porting.
4. **We would lose backends and fidelity.** No SDL3_GPU or Linux renderer, no APU/DSP emulation (our audio fixes
   for gameplay static and crash 0xE5318 live there), and the network stack we got System Link working on would be
   replaced by their `xnet` (777 lines). MM3 also leans on exact pushbuffer and fence behaviour (run-ahead, notify
   events, CPU-drawn load screens) that an API-level layer has to re-create call by call.
5. Our fork already has an API-level D3D8-to-D3D11 shim (`src/d3d`), which MM3 does not use (it runs through
   the NV2A path, and its D3D8LTCG library is linked into the game). So an API-level route already exists in-tree
   and is not what carries MM3.

## What is worth pulling (ranked)

1. **CPU calling convention (largest possible win, largest cost).** Their explicit-context ABI is the thing our
   notes say limits the game thread. Trying it means a recompiler change, not a patch: the recompiler and runtime
   come as a pair. Cheapest experiment: hand-port one hot function set in our generated code to a context-passing
   form and measure the frame time before deciding anything bigger.
2. **x87 handling.** Runtime-tracked control word (`fcw`) so precision/rounding follow the game, host-side CRT math
   (their note: CRT helpers branched on flags that did not survive call/ret and returned NaN at random), and a
   `fprem1` fix. Game-agnostic; fits the fork-stays-agnostic rule. Check our generated math calls first for the same
   stale-flag pattern before porting.
3. **XDK signature scanner (`xbe_symbols`).** Would let us find D3D/DSOUND functions automatically, and is the
   prerequisite for any hybrid where only the expensive D3D calls are intercepted. Needs signatures for build 5233,
   which means generating them from MM3 itself.
4. **Renderer details to check against `nv2a_d3d11.c`** (from their recent commit titles; not verified in their
   code): float/reverse depth for distant precision (ours is D24S8; may let us drop part of the draw-distance
   workaround), point sprites sized from the program's point size, refresh cap from the monitor's real refresh,
   texture-view reuse within a frame. We already skip identical pixel-constant uploads (`upload_ps_constants`).
5. **Smaller:** crash dumps beside the exe, an `X86_TRACED_FUNC`-style per-function trace, and their headless Linux
   harness idea for running generated code without a GPU.

## Open questions

- Whether their D12 `Backend::Draw(State)` interface could sit **behind** our NV2A decode (decode methods into a
  `State`, hand it to a backend). It would give SDL3_GPU and D3D12 backends one contract, but we have not tried it.
- How much of their kernel/XAPI layer overlaps ours (ours is about 40k lines in `src/kernel`); a diff would show
  which of their fixes are missing here.
- The project is two weeks old with one author; expect churn.

## Recommendation

Stay on our stack. Do experiment 1 under "worth pulling" (it is the only item that could move the frame-time
number), then item 2 (cheap, correctness), and treat the rest as reference reading.

## What was pulled across (2026-10-30)

| Idea | Outcome |
|---|---|
| Monitor-refresh frame cap | **Done** (fork `frame_limit.h`): `RECOMP_FPS_LIMIT=auto`, or unset, follows the display; launcher has a "Monitor" choice. Test added; measured 32.0 fps on this session's 32 Hz display. |
| Crash dumps | **Done** (fork `crash_report.c`): a minidump in `CrashDumps/` beside the exe, dbghelp loaded on demand. The test caught a real struct-packing bug. |
| SDL3 for input | **Done**: one pad path (SDL3 gamepads: Xbox, PlayStation, Switch, hot plug, rumble) on every platform, no XInput backend left. Launcher and debug overlay now read pads through a new `xbox_InputHostPad`; the pad state has a lock. Checked by running all three mission wins on the D3D11 build. |
| CPU calling convention | **Measured, not ported.** A sampling profiler of the game thread (`profile` pipe command, `tools/game_test/profile_thread.py`) shows ~31% of its time in translated code and ~67% blocked in ntdll waits, with no exe address above 1.2%. A context-passing ABI could only improve that minority and has no hot spot to target. The profile did find waste elsewhere, now fixed in the fork: the frame-request spin (`SwitchToThread` loop) became an event wait and `xbox_GuestMapped` got a short per-thread cache, together 2.72 to 2.20 CPU cores. |
| x87 / CRT math / `fprem1` | **Already covered** in the fork (`recomp_fprem` with the C2 fix, x87 trig and fprem tests in `tools/conformance`). Nothing to port. |
| Write-if-changed generation | **Already present** (`test_write_if_changed.py`). |
| Redundant state skipping | **Mostly present**: vertex/pixel shader, constant buffer and sampler binds are cached. Texture views are not, on purpose: binding render targets can unbind them, so a plain cache would be wrong. Left alone. |
| Point sprites | **Measured, not ported.** MM3 does draw point lists (night rain) but sets sizes 1.0 and 0.5 px (register values 8 and 4, in 1/8 px); D3D11 has no point size and a geometry-shader expansion is not worth a barely visible gain. |
| Float / reverse depth | Not ported: our depth follows the NV2A formats the game and the Y16 reinterpretation rely on. |
| XDK signature scanner | Not ported: signatures exist only for builds 4831/5849 and would have to be generated from MM3 (build 5233) first; `tools/func_id` already identifies library code here. |
| Bink fix, boot splash | Not applicable: MM3 ships no Bink files and has its own launcher and intro skip. |
| System Link by direct IP | Already covered by `RECOMP_NET_PEERS` tunnelling. |
