HOW TO USE THIS FILE
-------------------
Each detailed item below explains the symptom, upstream mechanism, local
evidence, integration work, dependencies, risks and acceptance checks. Source
paths are relative to the repository. Function addresses refer to the supported
retail Xbox code, not host addresses. Generated C line numbers can change after
regeneration; locate the function/address rather than relying on a line number.

Status meanings:
- MISSING: the upstream mechanism is absent from the checked local source.
- PARTIAL: some behavior is covered, but an identifiable gap remains.
- EQUIVALENT: a local implementation covers the audited behavior; preserve and
  verify it instead of replacing it solely to match commit ancestry.
- FEATURE: new functionality, not evidence of a bug in existing gameplay.
- DOCUMENTATION: no gameplay repair to port by itself.

Suggested implementation order:
1. Translation/correctness: missing 0x2534FF setter and unresolved-stub reports;
   collision-cell bounds; confirm already recovered graph/math functions.
2. Runtime liveness: interrupt preemption, audio queue/producer behavior, and
   bounded push-buffer producer run-ahead. Treat concurrency changes as separate
   reviewable units with targeted regressions and real startup/gameplay trials.
3. Rendering correctness: depth sampling/edge placement, menu/reset layout,
   facade pools and distance ownership, haze/foliage, then panorama sampling.
4. Optional observability and UI: opt-in spike diagnostics; generic title hooks;
   settings/mod/keymap launcher; teleport heading; higher-FPS validation.
The detailed dependencies in the entries take precedence over this broad order.

G-01. GENERAL 80-BIT FLD GENERATION; KEEP THE EXISTING THROTTLE/GEAR REPAIR
Status: COVERED INDEPENDENTLY for the affected math helper; MISSING generic
pinned-generator change. Priority: generation correctness before regeneration.

Upstream source:
https://github.com/MattSG/mm3-recomp/commit/fd112c691e91ba4a8a99340eaa4382798cef7de3
The generator hunk is backported from later toolkit commit cd491b1; the game
commit retains generator pin 967ec30f362dee229183b4e112e928cd41830484.
Latest upstream file: scripts/generate_mm3.py:33-57.

Symptoms and cause, from upstream's diff/message:
- The pinned lifter treated FLD tbyte (10-byte x87 extended precision) as MEMF,
  reading only four low significand bytes as a single-precision float.
- The CRT exponential range limit at guest address 0x00393816 is 32767.5 in
  extended precision. Its incorrect float read becomes zero, selecting the
  overflow path for ordinary nonzero arguments and capping throttle/gears.
- UPSTREAM REPORTED: player top speed rose from 19.2 to 51.1 units/second during
  a 30-second bench-save throttle test. This is not a local expected-speed
  assertion for every car/save/configuration.

Local source evidence:
- scripts/generate_mm3.py:30 pins 967ec30...; :36 uses the plain cache directory
  tools/.generator/967ec30f362d, without the upstream -fp80 suffix/patch.
- scripts/Generate-MM3RuntimeEntries.py:31-40 patches the operands listed in
  each entry's x87_extended_loads from MEMF to MEMFP80, accepting either form.
- mm3_runtime_entry_repairs.json:115-154 recovers x87 entries 0x9BB15, 0x9BB04,
  0x9BB11, 0x9B4E2, 0x9BC04, 0x9BC35, 0x9BC52, including 0x3937F8 and 0x393816.
- src/recomp/gen/recomp_runtime_entries.c:2910 uses MEMFP80(0x393816) inside
  sub_0009BC52; extended-infinity loads also use MEMFP80.
- CMakeLists.txt:82-84 keeps calls in the same generated translation unit
  directed to recovered definitions of 0x9BC04/0x9BC35/0x9BC52.
- The bypassed original in recomp_0008.c:68623 still contains MEMF(0x393816).
  That stale source alone is not proof the active gameplay helper is unfixed.

Concrete integration steps:
[ ] Apply the small 10-byte FLD hunk to the pinned cache copy, using an identity
    such as the upstream -fp80 cache suffix to avoid silently reusing old files.
[ ] Keep the generator pin; do not replace it wholesale with the latest lifter.
[ ] Verify the expected old hunk occurs exactly once before replacing it, and
    fail generation clearly if the pin or source layout unexpectedly changes.
[ ] Preserve the runtime-entry overlays, helper-unwinds-caller handling, guest
    x87 precision/control/stack rules and recovered-helper same-chunk routing.
[ ] Regenerate in a separate output directory first and compare all changed
    functions; do not overwrite known-working generated output without evidence.
[ ] Retain the overlay replacement's support for already-correct MEMFP80 input,
    so generic FLD support and runtime entry recovery are not conflicting fixes.

Risks and edge cases:
- All 10-byte FLD operands must be handled, not only constant 0x393816.
- This is not permission to treat 4-byte or 8-byte loads as extended precision.
- Duplicated helper definitions, wrong wrapper routing or double cleanup can
  corrupt x87 depth/ESP even when the numeric constant is correct.
- The current fork also repairs underflow and overflow helper continuation/
  caller-unwind behavior; upstream's generic FLD hunk does not replace those.

Planned regression and gameplay acceptance:
[ ] Run tests/mm3_x87_exp_regression.py: original-XBE comparisons, double-range
    limits, overflow helper cases, x87 stack, ESP, registers and control word.
[ ] Run tests/mm3_gearing_regression.py and factory-physics variants; preserve

[ ] Add focused generator cases for FLD sizes 4, 8 and 10, memory addressing,

[ ] Prove the final active generated/helper path contains MEMFP80 for every

G-02. RECOVER THE CAMERA FOV SETTER AT 0x2534FF
Status: PARTIAL for parent commit c91d8f1; this setter itself is MISSING.
Priority: register/stack integrity before broader gameplay/performance changes.

Upstream source:
https://github.com/MattSG/mm3-recomp/commit/c91d8f12cc73b257e90c380abeeb9ee6eba15707
Latest upstream mm3_runtime_entry_repairs.json:156 defines [0x2534FF,0x253512).

Symptoms and technical cause, from upstream:
- Camera field-of-view updates were skipped. Guest ESP remained four bytes
  lower than the original function's RET 4 would leave it.
- The caller then popped the float argument as ESI. Its parent restored corrupt
  EBX/ESI, and race path code subsequently treated a code address as an object.
- Upstream traced callee-save violations through 0x13FF6E/0xFF714/0xFA6DC,
  null calls at 0x13FF8C and 0x14E815, and crashes in 0x2D7C9.
- The original setter loads [ESP+4], calls 0x2513B6, then RET 4. It is reached
  by the this-adjusting thunk 0x6EC40, vtable 0x378D44 slot +0x38, from 0xFA704.
- UPSTREAM REPORTED: after this and the graph-epilogue recovery, six 130-second
  drives had no freezes/crashes, with null virtual calls reduced from hundreds
  to zero to two. This audit did not independently reproduce those counts.

Local source evidence:

  stub that only advances ESP by four, without executing the original body.
- recomp_0006.c:25098,25151,25196,25236,25268,25292 contains six generated
  thunk-tail references to sub_002534FF. This is a source-reference count;
  it does not prove six distinct sites all execute in a given race.
- mm3_runtime_entry_repairs.json has sub_002533EB at :177, a different setter
  already recovered. It is not a substitute for address 0x2534FF.
- No 0x2534FF recovered-entry case exists in recomp_runtime_entries.c.

Concrete integration steps:

[ ] Keep mm3_widescreen.c FOV/culling/chase-camera modifications separate and
    verify they consume the recovered camera state correctly.

Dependencies and risks:

G-05. GUARD COLLISION-CELL GRID RANGES AND FACE INDICES AT LOAD
Status: MISSING. Priority: freezes, memory corruption and lost road collision.

Upstream source:
https://github.com/MattSG/mm3-recomp/commit/9ad17627e2bd53d972fe7d44063b5ec7396327d6
Original file src/mm3_collision_cells.c; moved unchanged by 9118262 to
src/mods/collision_fix.c. Latest source: :25 sanitize, :45 sub_0015A929.

Symptoms and cause, from the upstream diff/message:
- Collision query functions 0x15B1B0 and 0x15B4E1 stamp a 16-bit visited marker
  at stamps[list[i]] with no face-index bounds check.
- The Paris race-start cell, key 0x3400, was observed upstream decoding face
  indices as large as 0xFFA4, beyond its face count; some grid ranges also
  extended beyond the face-index list.
- Stores at 0x15B42A/0x15B712 reached up to 128 KiB beyond the stamp array,
  damaging collision-cache ring pointers and neighboring cells. The lookup at
  0x4EB98 could loop forever; collision queries could crash or lose road faces.
- UPSTREAM REPORTED: around half of long steering/crash runs froze or crashed
  before the guard and none of six did after it. Do not present this as a local
  measured failure rate or proof all collision corruption is solved.
- Upstream explicitly leaves the reason the compressed cell input can differ
  between runs unresolved. This guard bounds decoded output; it is not a
  demonstrated correction of the underlying stream/decompression cause.

Structure and upstream behavior:
- sub_0015A929 is the cache loader/decompressor wrapper; entry uses g_esi cell.
- Cell header: face count +4, face-index list pointer +8, list length +0xC,
  grid pointer +0x10, stamp array +0x18, grid dimensions +0x44/+0x48/+0x4C.
- Upstream accepts faces 1..0xFFFF, list length <=0xFFFF, cells <=0x10000 and
  list/grid addresses in [0x10000,0x08000000).
- For each grid [lo,hi) range, clamp hi to list length and lo to hi; find a valid
  face index in that range, then replace invalid indices with a valid index.
  With no valid index found, upstream's keep value remains zero.
- Existing per-pass stamps suppress repeated-face work from replacement
  duplicates. Sanitize only a successful call that replaced the cached header
  pointer, indicating a newly decoded cell, rather than every cache hit.

Local source evidence:
- No src/mm3_collision_cells.c or equivalent cell sanitizer exists.
- CMakeLists.txt:69-70 lacks sub_0015A929 in definition-only wrapper hooks.
- Generated recomp_0014.c:22887 defines the original loader; collision queries
  call it at :23261,:23778,:24331,:24872.
- scripts/mm3_collision_call_seam.cmake fixes caller argument cleanup, not cell
  data bounds. Keep that separate existing repair.

Concrete integration steps:
[ ] Add the load-time sanitizer as a title-specific hook using the existing
    definition-only rewriting, so same-chunk calls still pass through it.
[ ] Preserve g_esi, success-result semantics, original return/ESP behavior and
    the distinction between successful decode, cache hit and load failure.
[ ] Retain the collision-call stack seam; neither fix replaces the other.
[ ] Validate the full list/grid spans with checked guest-address arithmetic,
    rather than checking only their starting pointers. Treat this as fork
    hardening in addition to the observed upstream guard, not a claim that
    upstream already performed full span validation.
[ ] Test checked grid-dimension multiplication before using its product.
    Upstream multiplies three uint32_t dimensions directly; overflow/spans are
    explicit source edge cases for integration fixtures, not locally observed
    corruption mechanisms in this audit.
[ ] Preserve valid cells byte-for-byte; define/log bounded repair counts only
    in opt-in diagnostics, keeping per-query hot paths quiet.
[ ] Keep this stability guard required if/when mods are introduced; upstream
    marks the collision fix required and cannot turn it off in its launcher.

Planned regression acceptance:
[ ] Synthetic actual-layout cells cover all-valid, invalid face at each end,
    mixed valid/invalid, empty range, all-invalid range, lo > hi, hi > length,
    zero faces, maximum face/list lengths, invalid pointers and dimension/span
    overflow. Assert no out-of-range writes and preserve unrelated RAM.
[ ] Verify replacements belong to a valid face and duplicate suppression does
    not invent additional collision-query results for already-valid cells.
[ ] Verify successful new decode sanitizes once, cache hit leaves valid state
    unchanged, and failure leaves original error path intact.
[ ] Test register/ESP/result preservation through the real loader wrapper.
[ ] Replay the Paris race start and drive at least two minutes with steering,
    road transitions, crashes, resets and teleports in cruise and missions.
[ ] Track freezes, invalid cells and falling-through-road incidents; compare
    identical save/config controls. Include ordinary 60 FPS runs, not only
    instrumented builds. Do not call the underlying stream cause resolved.


G-06. BOUND PUSH-BUFFER PRODUCER RUN-AHEAD TO AVOID DARK FRAMES
Status: MISSING. Historical unconditional-spin fix is SUPERSEDED by the bound.
Priority: visible one-frame lighting errors while preserving performance.

Upstream history:
https://github.com/MattSG/mm3-recomp/commit/3188791794f5bd54662aee74a4594fa901ce5f47
https://github.com/MattSG/mm3-recomp/commit/fdc33ea50553fa47aa146931ce189acf478afd85
Final title implementation: upstream src/recomp_manual.c:1128-1149,
sub_00344AB0; sampler addition later in 67e9443 is handled in G-07.

Symptoms and cause, from upstream:
- Making every WBC flush a bare store fence let the guest submit indefinitely
  ahead of the executor. Some frames then used tunnel-like lighting in daylight:
  scene dark, headlights on and night speedometer.
- UPSTREAM REPORTED: five to 22 dark frames per 1200-frame noon drive before;
  full waiting nearly eliminated them but cost about 21% of uncapped race FPS.
- Truthful fences, brightness-target writeback and serializing only BlockOnFence
  had not fixed both cruise and missions in upstream's investigation.
- Later fdc33ea waits only when producer lag exceeds 256 KiB, or the ring wraps
  between producer and GET. The exact mid-frame read racing the executor is
  explicitly still unidentified upstream. This bounds the race; it does not
  prove which result/read must be synchronized for a more exact future fix.
- UPSTREAM REPORTED: bounded run-ahead gave zero dark frames in the tested
  mission drives; uncapped race figures were 296 FPS for always-spin, 352 for
  256 KiB and 373 unbounded. These are not predictions for this PC/fork.

Exact final algorithm and local evidence:
- Upstream MM3_KICK_LAG = 0x40000 bytes.

R04. XAudio2 UNDERRUN CUSHION FOR CRACKLING DURING DRIVES
-------------------------------------------------------
Classification: MISSING at the output queue; local PCM queue fixes are separate.
Suggested priority: high audio reliability.
Upstream commit: 9b9a37c4f2de16acd6adab3b868aa7ef187143bd
https://github.com/MattSG/xboxrecomp/commit/9b9a37c4f2de16acd6adab3b868aa7ef187143bd

Cause and symptoms:
Capacity alone does not ensure queued playback slack. The 64-slot XAudio2
queue normally contains only audio produced so far, so repeated CPU/GPU hitches
can empty it and produce brief silence/clicks. Upstream primes an empty queue
with eight 256-sample silent buffers, approximately 43 ms at 48 kHz, before the
real samples. It does this on initial fill and after an underrun, and emits an
underrun diagnostic once for each detected empty transition.

Local evidence:
  tools/xboxrecomp/src/apu/apu_xaudio2.c, xa2_submit_samples near 193:
    checks BuffersQueued >= XA2_NUM_BUFS but has no XA2_CUSHION/empty priming.
  tools/xboxrecomp/src/apu/apu_dsp.c and apu_state.h contain the fork's pending
  PCM queue/head/consumption work. That queue preserves decoded frames; it does
  not provide the host playback cushion introduced by this commit.

Later implementation steps:
  a. Add startup/empty queue priming with silence whose storage remains alive
     through asynchronous playback. Keep silent buffer size compatible with
     actual submitted sample counts and channels.
  b. Respect total queue capacity, partial SubmitSourceBuffer failure and the
     real-buffer ring's ownership; never recycle a buffer still being played.
  c. Add bounded underrun counters/diagnostics for comparison, without changing
     guest PCM arithmetic or the fork's frame queue/consumed protocol.
  d. Evaluate the cushion with R05 and R11 independently so the reason for any
     improvement is visible. Do not use it to conceal a growing producer backlog.

Dependencies and edge risks:
R05 addresses producer scheduling, R11 addresses an ISR wait that stalls the
producer, and R07/R12 cover DSP headroom. Priming adds playback latency, can
delay the first audible sound and can insert a gap on refill; ensure reset,
pause/unpause, device recreation and shutdown do not repeatedly prime an
already healthy queue. Check mono/stereo assumptions, invalid sample lengths
and whether silence callbacks expect buffer context. Preserve attenuation,
HRTF and ADPCM decoding fixes.

Verification and acceptance:
Run the existing DSP/PCM queue suite. Compare identical long noon-drive routes
with logged empty-queue events and measured audio timing. Exercise race loads,
car resets, window resizing/focus changes, movies, pause, repeated start/stop
and a temporary CPU load. Listen for crackle and synchronization drift; verify
queued audio remains bounded. Upstream reported 8-14 underruns before and none
in the next two drives after priming. Repeat locally; do not promise the same
counts or zero underruns under all hardware/load conditions.

R05. APU PRODUCER THREAD PRIORITY / SCHEDULER DELAYS
-------------------------------------------------
Classification: MISSING. Suggested priority: measure after the audio cushion.
Upstream commit: a4c280095ce2a33f06be4e41735a8e29b576bea7
https://github.com/MattSG/xboxrecomp/commit/a4c280095ce2a33f06be4e41735a8e29b576bea7

Cause and symptoms:
The frame thread produces audio in bursts and then sleeps. Guest-raised host
thread priorities can delay its wake-up beyond the queued playback budget.
Upstream raises the Windows frame producer to THREAD_PRIORITY_TIME_CRITICAL
at thread entry. This attempts to preserve prompt wake-up; it does not shorten
DSP instructions or correct queue/interrupt logic.

Local evidence:
  tools/xboxrecomp/src/apu/apu_core.c, mcpx_apu_frame_thread near 560:
    enters with MCPX state and takes its lock, with no SetThreadPriority call.
  A SetThreadPriority in the local renderer applies to shader compilation
  workers, not this audio frame thread.

Later implementation steps:
  a. Introduce the Windows priority assignment at the frame-thread boundary
     and check/record failure in an appropriate bounded diagnostic.
  b. Compare time-critical with the existing policy using wake-up lateness,
     audio underruns and CPU utilization; retain a way to reproduce the old
     policy while evaluating it.
  c. Confirm the thread actually sleeps between bursts in this fork after the
     DSP and PCM fixes. Review all locks it holds and blocking operations.
  d. Preserve startup/shutdown state, thread/TIB/worker-stack initialization and
     platform guards; do not change every guest/device thread's priority.

Dependencies and edge risks:
R04 provides playback slack; R11 removes the dispatch-lock deadlock shape.
Higher priority cannot fix an APU ISR waiting for a lock held by the game.
This scheduling choice can starve lower-priority work if an unexpected spin,
lock wait or sustained overload appears. The upstream claim that the mostly

R11. DEVICE ISRS MUST PREEMPT DISPATCH_LEVEL WITHOUT ALLOWING DPC OVERLAP
------------------------------------------------------------------------
Classification: MISSING. Suggested priority: highest kernel/audio stability.
Upstream commit: d359ee07288bc54f0b42c18842deed60a99131f9
https://github.com/MattSG/xboxrecomp/commit/d359ee07288bc54f0b42c18842deed60a99131f9

Cause and symptoms:
DirectSound stops a voice while the guest game thread is at DISPATCH_LEVEL
and waits for the APU interrupt to clear a pending bit. The local dispatch
processor lock is also taken by the device ISR thread when crossing upward,
so the ISR waits for the same game thread that is spinning for the ISR.

the cycle. The APU also delayed interrupt delivery for fifty raised-IRQL polls,

  tools/xboxrecomp/src/kernel/kernel_hal.c, irql_track lines 208-212:
    every upward DISPATCH threshold crossing takes g_dispatch_lock.
  xbox_IrqlEnterInterrupt/Leave near 247-265 have no unlocked-device-ISR
  ownership flags or g_dispatch_owned/g_isr_unlocked tracking.
  tools/xboxrecomp/src/apu/apu_core.c, apu_deliver_irq near 144-153:
    held_off and xbox_IrqlBlocksInterrupts retain the fifty-poll gate.
  The fork's kernel_bridge.c has independent DPC queue/drain/exclusion,
  interrupt synchronization and lower-IRQL lifecycle changes that must survive.

Later implementation steps:
  a. Model a hardware ISR above DISPATCH_LEVEL separately from a DPC: allow a
     device interrupt entered from below DISPATCH to avoid the processor lock,
     while publishing its raised IRQL and retaining correct raised accounting.
  b. Track actual per-thread dispatch-lock ownership so leave/lower never
     releases a lock the ISR thread did not acquire.
  c. When a DPC is invoked from an unlocked ISR context, acquire the required
     processor exclusion for the DPC and release it using a distinct saved
     state flag. Cover nested contexts and all restoration paths.
  d. Remove the APU's inappropriate raised-DISPATCH holdoff only in the same
     coordinated change, preserving interrupt object/ISR synchronization and
     pending DPC semantics. Reconcile the local guest KfLowerIrql drain-before-

not resolve this lock cycle. Device ISR access can now overlap a guest at

destination-alpha blend draw (0x304/0x305). Choosing a coarser mip instead
reduced the alpha silhouette and exposed the underlying flat horizon band.
